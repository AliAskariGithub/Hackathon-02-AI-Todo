# Full-Stack Multi-User Todo Web Application Constitution

**Version**: 3.0.0 | **Ratified**: 2026-02-02 | **Last Amended**: 2026-02-11

## 1. Core Mission & Philosophy

### The Agent-First Mandate
This project is built entirely through Spec-Driven Development (SDD). All code, infrastructure YAML, and configuration must originate from specification files in `/specs`. No manual code or infrastructure edits are permitted during the development process. All changes must be generated by AI agents following the SDD workflow.

### The Evolution Principle
Every phase must build upon the previous. Phase-V transitions the system from direct service-to-service communication to an Event-Driven Architecture (EDA) using Dapr and Kafka. Each evolution preserves prior functionality while adding new capabilities.

### Decoupled Evolution
The system MUST transition from direct service-to-service communication to an Event-Driven Architecture (EDA). Services communicate asynchronously through events, enabling loose coupling, independent scaling, and resilient failure handling.

### Infrastructure Abstraction
Use Dapr (Distributed Application Runtime) as the universal interface for all infrastructure building blocks (State, Pub/Sub, Secrets, Jobs). Application code MUST remain cloud-agnostic—swapping infrastructure providers (e.g., Kafka for Redpanda) MUST require zero code changes.

### Cloud-Native Excellence
Prioritize portability, horizontal scalability, and automated recovery. Services must be designed for cloud-native environments with proper observability, resilience, and operational readiness.

## 2. Core Development Principles

### The Agentic Standard
No manual code or YAML. All logic, manifests, and pipelines MUST be generated via Spec-Driven Development (SDD) using Claude Code, Gordon, kubectl-ai, and Kagent. This ensures consistency, traceability, and adherence to architectural standards.

### Agentic Autonomy
All code must be generated by Claude Code via the Spec-Kit Plus workflow. Claude Code serves as the Orchestrator, coordinating specialized agents (Docker AI/Gordon, kubectl-ai, Kagent) for their respective domains. No manual code edits are permitted during the development process.

### Intelligence & Reliability
AI responses MUST be concise (Simple English, grade 6-8 reading level) but backed by technical JSON data for tool execution accuracy. This ensures accessibility while maintaining precision for automated task operations.

### Scheduling Standards
Use Dapr Jobs API for exact-time reminders and scheduled tasks. Polling-based cron jobs are PROHIBITED for user notifications. This ensures precise timing and reduces unnecessary resource consumption.

### Search & Discovery
Implement server-side filtering and sorting as the primary method for task retrieval. Client-side filtering should only be used for immediate UI responsiveness with small datasets.

### Live Documentation
Use Context7 MCP Server for all real-time documentation fetches regarding Next.js 16.1.2, Better Auth, FastAPI, Kubernetes, Helm, Dapr, and Kafka. This ensures accurate, up-to-date technical information for all technology decisions.

### Secure by Default
Authentication and user isolation (ownership enforcement) are non-negotiable architectural requirements. All user data must be properly isolated and protected. Containers must not run as root. Secrets must never be hardcoded.

### Modernity
Leverage the latest features of Next.js 16 (App Router), Shadcn UI, Kubernetes, Helm, Dapr, and Kafka. The application must utilize modern development practices and current technology standards.

## 3. Infrastructure-as-Code (IaC) Standards

### Helm Primary
All Kubernetes resources MUST be managed via Helm Charts in the `/charts` directory. Raw manifests are permitted only for temporary debugging and must not be committed to the repository. Helm is the single source of truth for infrastructure.

### Stateless Services
Both Frontend and Backend MUST remain stateless. Persistence is offloaded to Neon PostgreSQL (external managed service) or managed Kubernetes volumes. No application state may be stored in container filesystems.

### Standardized Labels
Every Kubernetes resource MUST include the following labels:
- `app.kubernetes.io/name`: Component name
- `app.kubernetes.io/instance`: Release instance name
- `app.kubernetes.io/version`: Semantic version
- `app.kubernetes.io/component`: Component type (frontend/backend/database)
- `app.kubernetes.io/part-of`: Application name (ai-todo)
- `app.kubernetes.io/managed-by`: Helm

## 4. Distributed Runtime (Dapr) Standards

### Sidecar Pattern (Mandatory)
Every microservice pod MUST be injected with a Dapr sidecar. This is enforced via the `dapr.io/enabled: "true"` annotation on all Deployments. The sidecar provides service-to-service communication, state management, pub/sub, and secrets access.

### Component Portability
Dapr components (State, Pub/Sub, Secrets, Jobs) MUST be defined in YAML configuration files. Application code MUST remain cloud-agnostic—swapping infrastructure providers (e.g., Kafka for Redpanda, Redis for Valkey) MUST require zero code changes, only component YAML updates.

### Building Block Usage
- **State Management**: Use Dapr State API for all persistent data operations
- **Pub/Sub**: Use Dapr Pub/Sub API for all event publishing and subscription
- **Secrets**: Use Dapr Secrets API for all credential and configuration access
- **Jobs**: Use Dapr Jobs API for scheduled tasks and reminders

### Dapr Component Naming
All Dapr component files MUST follow the naming convention: `<component-type>-<provider>.yaml` (e.g., `pubsub-kafka.yaml`, `statestore-postgresql.yaml`, `secretstore-kubernetes.yaml`).

## 5. Event Streaming (Kafka) Standards

### Strimzi Governance
Local Kafka instances MUST be managed by the Strimzi Operator. This ensures consistent Kafka cluster management, monitoring, and upgrades across environments.

### Event Schema Standardization
All events MUST follow a standardized JSON schema including:
- `event_type`: String identifier for the event type (e.g., "task.created", "task.updated")
- `payload`: Object containing event-specific data
- `user_id`: String identifier for the user who triggered the event
- `timestamp`: ISO 8601 timestamp of when the event occurred
- `correlation_id`: UUID for tracing related events across services

Example:
```json
{
  "event_type": "task.created",
  "payload": {
    "task_id": "123",
    "title": "Buy groceries",
    "status": "pending"
  },
  "user_id": "user-456",
  "timestamp": "2026-02-11T10:30:00Z",
  "correlation_id": "abc-def-ghi"
}
```

### Topic Naming Convention
Kafka topics MUST follow the pattern: `<domain>.<entity>.<action>` (e.g., `todo.task.created`, `todo.task.updated`, `todo.notification.sent`).

### Cloud Provider Neutrality
While targeting Azure (AKS) or Oracle (OKE), Helm charts MUST remain generic enough for any CNCF-compliant Kubernetes cluster. Provider-specific features should be abstracted through Dapr components.

## 6. Containerization Standards

### Multi-Stage Builds
All Dockerfiles MUST use multi-stage builds to minimize image size and maximize security. Build dependencies must be separated from runtime dependencies. Final images should contain only runtime essentials.

### Non-Root Execution
Containers MUST NOT run as `root`. Each Dockerfile must create and use a dedicated `appuser` with minimal privileges. The USER directive must be set before the ENTRYPOINT/CMD.

### Semantic Versioning
Container images MUST be tagged with semantic versioning (e.g., `v1.0.4`) and git commit SHA. The `latest` tag MUST NOT be used in production manifests or Helm values. All image references must be pinned to specific versions.

### Image Security
- Base images must be from official sources or verified registries
- Images must be scanned for vulnerabilities before deployment
- Minimize layers and remove unnecessary packages
- Use `.dockerignore` to exclude sensitive files and build artifacts

## 7. AIOps & Agent Governance

### Tool-Specific Responsibilities

**Claude Code (The Orchestrator)**
- Responsible for writing `/specs` and generating `/plans`
- Orchestrates logic refactors and CI/CD setup
- Coordinates all other agents and ensures workflow compliance
- Creates Prompt History Records (PHRs) for all work
- Suggests Architecture Decision Records (ADRs) for significant decisions

**Docker AI / Gordon (The Container Architect)**
- Responsible for generating, auditing, and optimizing all `Dockerfile` configurations
- Optimizes multi-service container builds for new microservices (Notification, Recurring Task, Audit)
- Ensures multi-stage builds and security best practices
- Optimizes image size and build performance
- Reviews docker-compose configurations

**kubectl-ai (The Manifest Generator)**
- Used for generating initial Kubernetes resource templates
- Generates complex Dapr component manifests (State, Pub/Sub, Secrets, Jobs)
- Generates Kafka/Strimzi resource definitions
- Executes scaling commands and resource updates
- Assists with kubectl operations and cluster interactions

**Kagent (The SRE & Health Auditor)**
- Responsible for cluster health audits and monitoring
- Performs SRE-level health audits on the distributed mesh
- Validates Dapr sidecar injection and component health
- Troubleshoots "CrashLoopBackOff" and other runtime issues
- Performs resource optimization and capacity planning
- Validates deployment health and readiness

### The Safeguard Clause
Any code or YAML generated by an AI agent MUST be reviewed by the Technical Lead (the user) before final deployment to the Minikube cluster. Agents propose; humans approve and deploy.

## 8. Development Workflow (SDD 2.0)

### The Five-Step Process

1. **Draft**: Create or update a specification in `/specs/phase-v/`
2. **Plan**: Run `/sp.plan` to generate the implementation blueprint with architecture decisions
3. **Execute**: Use the appropriate AIOps tool (Gordon for Docker, kubectl-ai for Dapr/Kafka manifests)
4. **Validate**: Use `kagent "check health"` to confirm successful deployment, Dapr sidecar injection, and cluster health
5. **Record**: Log every successful iteration in the project's Prompt History Record (PHR)

### Workflow Enforcement
- No step may be skipped
- Each step must complete successfully before proceeding
- All work must be traceable through PHRs
- Significant architectural decisions must be documented in ADRs

## 10. Application Architecture Standards

### Tech Stack Compliance
Use the specified technology stack without deviation. Any technology substitutions require explicit architectural approval and ADR documentation.

### Event-Driven Communication
Services MUST communicate asynchronously through Dapr Pub/Sub for all non-synchronous operations. Direct HTTP calls between services are permitted only for synchronous request-response patterns that require immediate feedback.

### Auth Protocol
Implement Better Auth JWT Plugin with shared `BETTER_AUTH_SECRET` for cross-service verification. Authentication must be consistent across all services and container instances.

### API Design Standards
Design RESTful endpoints with strict user-id path parameter validation and JWT middleware filtering. All API endpoints must follow consistent design patterns and return proper HTTP status codes.

### UI/UX Standards
Implement responsive design using Shadcn UI components with a mobile-first approach. The user interface must be accessible and intuitive across all device sizes and meet WCAG 2.1 AA standards.

### Data Integrity Requirements
Maintain database transactions via SQLModel with Neon-specific connection pooling for serverless environments. All data operations must preserve ACID properties.

## 11. Security & Compliance Constraints

### Security Enforcement
- All API requests MUST return 401 Unauthorized if a valid JWT is missing
- Security measures MUST be implemented at every layer (network, container, application)
- Kubernetes NetworkPolicies MUST restrict pod-to-pod communication
- Secrets MUST be managed via Kubernetes Secrets or Azure Key Vault
- All credentials MUST be accessed exclusively via the Dapr Secrets API

### Secrets Management (Dapr Mandatory)
- All credentials MUST be stored in Kubernetes Secrets or Azure Key Vault
- Application code MUST access secrets exclusively via the Dapr Secrets API
- Direct access to Kubernetes Secrets or environment variables for sensitive data is PROHIBITED
- Required secrets: `BETTER_AUTH_SECRET`, `DATABASE_URL`, `JWT_SECRET`, `KAFKA_BOOTSTRAP_SERVERS`
- No hardcoded credentials or secrets are allowed in code or container images

### Environment Management
- `.env` files are permitted for local development only
- `.env` files MUST be in `.gitignore` and never committed
- Production environments MUST use Kubernetes Secrets accessed via Dapr
- Secret rotation procedures must be documented and tested

### Architecture Boundaries
- Frontend and Backend MUST remain separate services communicating over HTTPS/REST
- Service boundaries must be maintained to ensure proper separation of concerns
- No direct database access from frontend
- All inter-service communication must be authenticated
- Event-driven communication must use Dapr Pub/Sub with proper topic access controls

## 12. Operational Standards

### Observability Requirements
- All services MUST expose health check endpoints (`/health`, `/ready`)
- Structured logging MUST be implemented (JSON format preferred)
- Metrics MUST be exposed in Prometheus format where applicable
- Distributed tracing MUST be enabled to visualize the flow of messages from the Chatbot, through Kafka, to downstream services (Notification, Recurring Task, Audit)
- Dapr tracing must be configured with appropriate sampling rates

### Distributed Tracing Standards
- Use Dapr's built-in tracing capabilities with OpenTelemetry
- Trace context must be propagated across all service boundaries
- Critical paths (user request → event → service processing) must be fully traceable
- Trace sampling should be configured based on environment (100% in dev, adaptive in production)
- Tracing backends (Zipkin, Jaeger) must be configured via Dapr Configuration

### Resource Management
- All Kubernetes resources MUST define resource requests and limits
- Horizontal Pod Autoscaling (HPA) should be configured for production workloads
- Resource quotas should be defined per namespace
- Pod disruption budgets should be configured for high-availability services

### Deployment Standards
- Rolling updates MUST be the default deployment strategy
- Readiness and liveness probes MUST be configured for all pods
- Zero-downtime deployments are required for production
- Rollback procedures must be documented and tested

### CI/CD Validation
- GitHub Actions MUST include a "Dapr Validation" step to ensure sidecars and components are healthy before deployment
- Automated tests must verify event publishing and consumption
- Integration tests must validate end-to-end event flows
- Deployment pipelines must validate Dapr component configurations

## 13. Success Criteria

### Authentication Functionality
Users can sign up and sign in via Better Auth. The authentication system must be reliable, secure, and work consistently across all container instances.

### User Data Isolation
Users can only see, create, and modify their own tasks (enforced via JWT & User ID). Data isolation must be enforced at the API and database levels, regardless of which pod serves the request.

### Cross-Device Compatibility
Application is fully functional on both desktop and mobile views. Responsive design must provide optimal user experience across all devices.

### Agentic Development Compliance
Achieve 0 manual lines of code written by the developer; all changes logged via agentic tasks. The entire development process must follow the SDD 2.0 workflow.

### Cloud-Native Readiness
- Services scale horizontally without data loss or session disruption
- System recovers automatically from pod failures
- Zero-downtime deployments are achievable
- Infrastructure is fully reproducible via Helm charts

### Event-Driven Architecture Readiness (Phase-V)
- All services communicate asynchronously through Dapr Pub/Sub for non-synchronous operations
- Events follow standardized schema with proper correlation IDs for tracing
- Kafka topics are properly configured and accessible via Dapr components
- Dapr sidecars are successfully injected into all microservice pods
- Distributed tracing visualizes complete message flows from source to destination
- Scheduled tasks use Dapr Jobs API (no polling-based cron jobs for user notifications)
- Infrastructure changes (swapping Kafka for Redpanda) require zero code changes

## 14. Governance

### Amendment Procedure
All development activities must comply with the principles outlined in this constitution. Any deviations require:
1. Explicit architectural approval from the Technical Lead
2. Documentation in an Architecture Decision Record (ADR)
3. Update to this constitution if the deviation becomes a new standard
4. Version bump following semantic versioning rules

### Compliance Review
- Code reviews must verify adherence to all constitutional principles
- Pre-deployment checklists must validate infrastructure standards
- Regular audits of container security and Kubernetes configurations
- PHR completeness checks for all significant work
- Dapr component validation before deployment
- Event schema compliance verification

### Version Control
- **MAJOR**: Backward-incompatible governance/principle changes or architectural paradigm shifts
- **MINOR**: New principles/sections added or materially expanded guidance
- **PATCH**: Clarifications, wording improvements, typo fixes, non-semantic refinements

### Authority
This constitution serves as the authoritative source for development standards and practices. In case of conflict between this document and other documentation, this constitution takes precedence.
