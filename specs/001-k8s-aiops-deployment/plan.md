# Implementation Plan: Local Kubernetes & AIOps Deployment

**Branch**: `001-k8s-aiops-deployment` | **Date**: 2026-02-08 | **Spec**: [spec.md](./spec.md)
**Input**: Feature specification from `/specs/001-k8s-aiops-deployment/spec.md`

## Summary

Deploy the existing AI Todo full-stack application (Next.js frontend + FastAPI backend) to a local Minikube Kubernetes cluster using AI-generated infrastructure code. All Dockerfiles, Helm charts, and Kubernetes manifests will be generated by specialized AI agents (Gordon for Docker, kubectl-ai for K8s, Claude Code for orchestration). The deployment will maintain the existing application functionality while adding cloud-native capabilities including service discovery, health checks, resource management, and automated recovery. The external Neon PostgreSQL database remains unchanged, with containers connecting to it via environment variables.

## Technical Context

**Language/Version**:
- Frontend: Node.js 20+ (Next.js 16.1.2, React 19.2.3, TypeScript 5)
- Backend: Python 3.11+ (FastAPI, SQLModel, asyncpg)
- Infrastructure: Bash/PowerShell for automation scripts

**Primary Dependencies**:
- Frontend: Next.js 16.1.2, React 19.2.3, Tailwind CSS 4, shadcn/ui, Framer Motion, Zustand, Better Auth

- Infrastructure: Docker Desktop 4.53+, Minikube, Helm 3+, kubectl
- AI Agents: Gordon (Docker AI), kubectl-ai, Kagent

**Storage**:
- Database: External Neon PostgreSQL (serverless) - NOT containerized
- Application State: Stateless containers (no persistent volumes for app state)
- Configuration: Kubernetes Secrets and ConfigMaps

**Testing**:
- Container Security: Gordon audit (`docker ai "rate my Dockerfile"`)
- Kubernetes Validation: kubectl-ai diagnostics (`kubectl-ai "check why pods are failing"`)
- Cluster Health: Kagent analysis (`kagent "optimize resource allocation"`)
- Application Testing: Manual verification of all features (auth, tasks, chat) in containerized environment

**Target Platform**:
- Local Development: Minikube cluster with Docker driver on Windows/macOS/Linux
- Container Runtime: Docker Desktop 4.53+ (required for Gordon compatibility)
- Orchestration: Kubernetes 1.28+ (Minikube default)

**Project Type**: Infrastructure (containerization + orchestration for existing web application)

**Performance Goals**:
- Container Build Time: <3 minutes for incremental builds
- Image Size: Frontend <500MB, Backend <300MB (multi-stage optimization)
- Pod Startup Time: <2 minutes from Helm install to Running state
- Application Response Time: <50ms additional latency vs non-containerized (service mesh overhead)
- Deployment Time: <5 minutes for full build-to-deploy cycle

**Constraints**:
- Local Minikube only (no cloud deployment)
- Docker driver required (no alternative runtimes)
- All infrastructure code AI-generated (zero manual YAML)
- External database (Neon PostgreSQL) - containers connect via DATABASE_URL
- Frontend must resolve backend via Kubernetes DNS (http://backend-service:8001)
- Resource limits: 4GB RAM, 2 CPU cores minimum for Minikube

**Scale/Scope**:
- Services: 2 (frontend, backend)
- Replicas: 1-2 per service (local development scale)
- Helm Charts: 1 umbrella chart with 2 subcharts
- Dockerfiles: 2 (frontend, backend) with multi-stage builds
- AI Agents: 3 (Gordon, kubectl-ai, Kagent)
- Automation Scripts: 1 deploy.sh for build-to-deploy workflow

## Architecture Decision Records (ADRs)

**Significant Decisions Requiring ADR Documentation**:

1. **ADR-001: Local Minikube vs Cloud Kubernetes**
   - Decision: Use Minikube for local development only
   - Rationale: Faster iteration, no cloud costs, constitutional constraint
   - Trade-offs: Not production-representative, limited scalability testing

2. **ADR-002: Helm as Sole IaC Mechanism**
   - Decision: All Kubernetes resources managed via Helm charts
   - Rationale: Constitutional requirement, version control, templating
   - Trade-offs: Learning curve, additional abstraction layer

3. **ADR-003: External Database (Neon PostgreSQL)**
   - Decision: Keep database external, do not containerize
   - Rationale: Existing production database, serverless benefits, stateless containers
   - Trade-offs: Network dependency, cannot test fully offline

4. **ADR-004: AI-Generated Infrastructure Code**
   - Decision: Use Gordon/kubectl-ai/Kagent for all infrastructure generation
   - Rationale: Constitutional mandate, consistency, best practices enforcement
   - Trade-offs: Agent availability dependency, review overhead

5. **ADR-005: NodePort for Frontend Access**
   - Decision: Use NodePort service type for frontend (with optional LoadBalancer via minikube tunnel)
   - Rationale: Simple local access, no ingress controller required
   - Trade-offs: Non-standard port, not production-like
