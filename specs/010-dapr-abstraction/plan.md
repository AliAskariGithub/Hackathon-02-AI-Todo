**Branch**: `010-dapr-abstraction` | **Date**: 2026-02-11 | **Spec**: [spec.md](./spec.md)

**Note**: This plan implements Phase-V Event-Driven Architecture with Dapr infrastructure abstraction, recurring tasks, intelligent reminders, and enhanced search/filtering capabilities.

## Summary

Refactor the FastAPI backend to use Dapr SDK for all infrastructure operations (State, Pub/Sub, Secrets, Jobs), eliminating direct dependencies on Kafka, PostgreSQL drivers, and environment variables. Implement recurring task automation (Daily/Weekly/Monthly), time-based reminders via Dapr Jobs API, multi-level priorities (High/Medium/Low), and server-side search/filtering with natural language chatbot integration. Upgrade Next.js frontend to use App Router patterns and Dapr Service Invocation for backend communication.

**Key Technical Approach:**
- Dapr sidecar pattern for all backend services
- Event-driven architecture with standardized event schema
- Infrastructure abstraction layer isolating application logic from infrastructure concerns
- Recurring task generation via event subscription to `todo.task.completed`
- Precise reminder scheduling via Dapr Jobs API (no polling)
- Server-side filtering and sorting for optimal performance

## Event-Driven Architecture Decisions (Phase-V)

### Communication Pattern

**Synchronous (HTTP/REST)**:
- Task CRUD operations (create, read, update, delete) - require immediate response for UI feedback
- Search/filter/sort operations - require immediate results for user experience
- Reminder scheduling - require immediate confirmation of scheduled time
- User authentication - require immediate JWT validation

**Asynchronous (Events)**:
- Recurring task generation - triggered by `todo.task.completed` event, eventual consistency acceptable
- Reminder delivery - triggered by Dapr Jobs API callback, fire-and-forget notification
- Task analytics/audit logging - eventual consistency acceptable for non-critical operations

**Rationale**:
- Synchronous operations provide immediate feedback for user-facing actions where latency matters
- Asynchronous operations decouple task completion from recurring instance generation, preventing blocking
- Event-driven recurring tasks enable horizontal scaling (multiple workers can process events)
- Dapr Jobs API provides precise timing for reminders without polling overhead

**Tradeoffs**:
- Eventual consistency for recurring tasks means slight delay (typically <1s) before next instance appears
- Event-driven architecture adds complexity but enables loose coupling and independent scaling
- Synchronous search operations may become bottleneck at scale (future optimization: caching layer)

### Dapr Components Required

- [x] **State Store**: PostgreSQL (Neon) - stores task data, recurrence patterns, reminders
  - Component: `statestore-postgresql.yaml`
  - Provider: `postgresql`
  - Connection: Via Dapr Secrets API (DATABASE_URL from Kubernetes Secret)

- [x] **Pub/Sub**: Kafka (Strimzi) - event streaming for task lifecycle events
  - Component: `pubsub-kafka.yaml`
  - Provider: `kafka`
  - Topics: `todo.task.created`, `todo.task.completed`, `todo.task.updated`, `todo.reminder.scheduled`
  - Connection: Via Dapr Secrets API (KAFKA_BOOTSTRAP_SERVERS from Kubernetes Secret)

- [x] **Secrets**: Kubernetes Secrets - stores DATABASE_URL, BETTER_AUTH_SECRET, JWT_SECRET, KAFKA_BOOTSTRAP_SERVERS
  - Component: `secretstore-kubernetes.yaml`
  - Provider: `kubernetes`
  - Scope: Namespace-scoped secrets

- [x] **Jobs**: Dapr Jobs API - schedules reminders at exact times
  - Built-in Dapr capability (no separate component file required)
  - Callback endpoint: `/api/reminders/callback`
  - Scheduling: ISO 8601 datetime format

### Event Schema Design

**Events to Publish**:

1. `todo.task.created`
   - Payload: `{ "task_id": "uuid", "title": "string", "user_id": "string", "priority": "High|Medium|Low", "due_date": "ISO8601", "recurrence": "Daily|Weekly|Monthly|null" }`
   - Consumers: Analytics service (future), Audit service (future)

2. `todo.task.completed`
   - Payload: `{ "task_id": "uuid", "user_id": "string", "completed_at": "ISO8601", "recurrence": "Daily|Weekly|Monthly|null" }`
   - Consumers: Recurrence service (generates next instance if recurrence pattern exists)

3. `todo.task.updated`
   - Payload: `{ "task_id": "uuid", "user_id": "string", "updated_fields": ["priority", "due_date"], "old_values": {}, "new_values": {} }`
   - Consumers: Analytics service (future), Audit service (future)

4. `todo.reminder.scheduled`
   - Payload: `{ "reminder_id": "uuid", "task_id": "uuid", "user_id": "string", "scheduled_time": "ISO8601" }`
   - Consumers: Notification service (mock logger in this spec)

**Events to Subscribe**:

1. `todo.task.completed`
   - Handler: `recurrence_service.py::handle_task_completed()`
   - Action: Check if task has recurrence pattern, calculate next due date, create new task instance via Dapr State API
   - Idempotency: Check for existing next instance by correlation_id to prevent duplicates

### Distributed Tracing Strategy

**Critical Paths**:
1. User creates recurring task → Task created → Event published → Next instance generated (on completion)
2. User schedules reminder → Reminder scheduled → Dapr Job created → Callback fired at scheduled time
3. User searches tasks → Backend filters → Results returned → Frontend displays

**Correlation ID Propagation**:
- Generated at API entry point (UUID v4)
- Included in all event payloads (`correlation_id` field)
- Propagated through Dapr Pub/Sub headers
- Logged in all service operations for trace reconstruction

**Sampling Rate**:
- Development (Minikube): 100% sampling for full visibility
- Production (AKS/OKE): Adaptive sampling (100% for errors, 10% for success) to reduce overhead

**Tracing Backend**:
- Zipkin (lightweight, easy Minikube setup)
- Configured via Dapr Configuration resource
- Accessible at `http://localhost:9411` (port-forwarded)

### Cloud Provider Neutrality

**Provider-Specific Features Used**:
- None - all infrastructure accessed via Dapr components

**Abstraction Strategy**:
- PostgreSQL: Dapr State Store component (`statestore-postgresql.yaml`) - can swap to Redis by changing component YAML
- Kafka: Dapr Pub/Sub component (`pubsub-kafka.yaml`) - can swap to Redpanda, RabbitMQ, or Azure Service Bus by changing component YAML
- Secrets: Dapr Secrets component (`secretstore-kubernetes.yaml`) - can swap to Azure Key Vault, AWS Secrets Manager by changing component YAML

**Migration Path**:
1. Update Dapr component YAML files (e.g., change `pubsub-kafka.yaml` to `pubsub-redpanda.yaml`)
2. Update Kubernetes Secrets with new connection strings
3. Redeploy Helm chart with new component configurations
4. **Zero application code changes required**

**Example Migration (Kafka → Redpanda)**:
```yaml
# Before: pubsub-kafka.yaml
apiVersion: dapr.io/v1alpha1
kind: Component
metadata:
  name: pubsub
spec:
  type: pubsub.kafka
  metadata:
  - name: brokers
    value: "kafka:9092"

# After: pubsub-redpanda.yaml
apiVersion: dapr.io/v1alpha1
kind: Component
metadata:
  name: pubsub
spec:
  type: pubsub.kafka  # Redpanda is Kafka-compatible
  metadata:
  - name: brokers
    value: "redpanda:9092"
```

Application code remains unchanged:
```python
# Same code works with both Kafka and Redpanda
await dapr_client.publish_event(
    pubsub_name="pubsub",
    topic_name="todo.task.created",
    data=event_payload
)
```
