**Feature**: Local Event-Driven Backbone

## Overview

This document defines the data models, event schemas, entity relationships, and state transitions for the event-driven architecture.

## Event Schemas

All events follow a standardized JSON schema with the following base structure:

```json
{
  "event_type": "string",
  "payload": {},
  "user_id": "string",
  "timestamp": "ISO 8601 string",
  "correlation_id": "UUID string"
}
```

### 1. task.created

**Description**: Published when a new task is created by a user or generated by the Recurring Task Service.

**Schema**:
```json
{
  "event_type": "task.created",
  "payload": {
    "task_id": "string (UUID)",
    "title": "string",
    "description": "string | null",
    "status": "pending | in_progress | completed",
    "priority": "low | medium | high",
    "due_date": "ISO 8601 string | null",
    "is_recurring": "boolean",
    "recurrence_pattern": "daily | weekly | monthly | null",
    "recurrence_interval": "integer | null",
    "recurrence_day_of_week": "integer (0-6) | null",
    "recurrence_day_of_month": "integer (1-31) | null",
    "parent_task_id": "string (UUID) | null",
    "tags": ["string"],
    "created_at": "ISO 8601 string"
  },
  "user_id": "string (UUID)",
  "timestamp": "ISO 8601 string",
  "correlation_id": "string (UUID)"
}
```

**Triggers**:
- User creates task via UI
- Recurring Task Service generates next instance

**Consumers**:
- Frontend (SSE) - Updates task list in real-time
- Audit Service - Logs task creation event

## Entity Relationships

### Task Entity

**Primary Entity**: Represents a user's todo item.

**Attributes**:
- `id` (UUID, Primary Key)
- `user_id` (UUID, Foreign Key to User)
- `title` (String, Required)
- `description` (String, Optional)
- `status` (Enum: pending, in_progress, completed)
- `priority` (Enum: low, medium, high)
- `due_date` (DateTime, Optional)
- `is_recurring` (Boolean)
- `recurrence_pattern` (Enum: daily, weekly, monthly, Optional)
- `recurrence_interval` (Integer, Optional)
- `recurrence_day_of_week` (Integer 0-6, Optional)
- `recurrence_day_of_month` (Integer 1-31, Optional)
- `parent_task_id` (UUID, Optional, Self-referencing for recurring tasks)
- `tags` (Array of Strings)
- `created_at` (DateTime)
- `updated_at` (DateTime)
- `completed_at` (DateTime, Optional)

**Relationships**:
- Belongs to User (many-to-one)
- Has many Reminders (one-to-many)
- Has parent Task (self-referencing, optional)

---

### User Entity

**Primary Entity**: Represents an authenticated user.

**Attributes**:
- `id` (UUID, Primary Key)
- `email` (String, Unique)
- `username` (String, Unique)
- `password_hash` (String)
- `created_at` (DateTime)
- `updated_at` (DateTime)

**Relationships**:
- Has many Tasks (one-to-many)
- Has many Reminders (one-to-many)

---

### Reminder Entity

**Primary Entity**: Represents a scheduled notification for a task.

**Attributes**:
- `id` (UUID, Primary Key)
- `task_id` (UUID, Foreign Key to Task)
- `user_id` (UUID, Foreign Key to User)
- `scheduled_time` (DateTime)
- `message` (String)
- `job_name` (String, Dapr Job identifier)
- `status` (Enum: pending, sent, cancelled)
- `created_at` (DateTime)
- `sent_at` (DateTime, Optional)

**Relationships**:
- Belongs to Task (many-to-one)
- Belongs to User (many-to-one)

---

### AuditLog Entity

**Primary Entity**: Represents a system event for observability and compliance.

**Attributes**:
- `id` (UUID, Primary Key)
- `event_type` (String)
- `event_payload` (JSON)
- `user_id` (UUID, Optional)
- `correlation_id` (UUID)
- `service_name` (String)
- `timestamp` (DateTime)

**Relationships**:
- None (append-only log)

## State Transitions

### Task Lifecycle

```
[Created] → [Pending]
    ↓
[In Progress]
    ↓
[Completed] → [Archived/Deleted]
```

**State Transition Rules**:
1. **Created → Pending**: Task created by user or Recurring Task Service
2. **Pending → In Progress**: User starts working on task
3. **In Progress → Completed**: User marks task as done
4. **Completed → Archived**: Task remains in database for history
5. **Any State → Deleted**: User permanently deletes task

**Event Triggers**:
- `task.created` → State: Pending
- `task.updated` (status: in_progress) → State: In Progress
- `task.completed` → State: Completed
- `task.deleted` → State: Deleted (removed from database)

---

### Recurring Task Generation Flow

```
[User Completes Recurring Task]
    ↓
[task.completed event published]
    ↓
[Recurring Task Service receives event]
    ↓
[Check idempotency (correlation_id)]
    ↓
[Calculate next due date based on pattern]
    ↓
[Create new task via Dapr Service Invocation]
    ↓
[task.created event published]
    ↓
[Frontend receives event via SSE]
    ↓
[New task appears in UI]
```

**Recurrence Pattern Logic**:
- **Daily**: `next_due_date = completed_date + recurrence_interval days`
- **Weekly**: `next_due_date = completed_date + (recurrence_interval * 7) days`
- **Monthly**: `next_due_date = completed_date + recurrence_interval months, same day_of_month`

**Idempotency Check**:
- Use `correlation_id` from `task.completed` event
- Store processed correlation IDs in Dapr State Store with 24-hour TTL
- Skip processing if correlation ID already exists

---

### Reminder Scheduling Flow

```
[User Sets Reminder]
    ↓
[Backend creates Reminder entity]
    ↓
[Backend schedules Dapr Job]
    ↓
[reminder.scheduled event published]
    ↓
[Dapr Jobs API waits until scheduled_time]
    ↓
[Dapr calls Notification Service callback]
    ↓
[Notification Service logs notification]
    ↓
[notification.sent event published]
    ↓
[Audit Service captures event]
```

**Reminder Cancellation**:
- If task completed before reminder time: Cancel Dapr Job
- If task deleted: Cancel Dapr Job
- Update Reminder entity status to "cancelled"

## Data Consistency Guarantees

### Event Ordering
- **Per-User Ordering**: Guaranteed by using `user_id` as partition key for task events
- **Global Ordering**: Not guaranteed across users (acceptable for this use case)
- **Reminder Ordering**: Guaranteed by single partition for reminder topic

### Idempotency
- All event consumers implement idempotency checks using `correlation_id`
- Processed events stored in Dapr State Store with TTL
- Duplicate events result in no-op (return success without processing)

### Eventual Consistency
- Frontend may briefly show stale data during event propagation
- SSE connection ensures updates arrive within 2 seconds (per success criteria)
- No strong consistency required for task management use case

## Storage Requirements

### Database (PostgreSQL via Neon)
- **Tasks Table**: ~1KB per task, estimated 10,000 tasks per user
- **Users Table**: ~500 bytes per user, estimated 1,000 users
- **Reminders Table**: ~500 bytes per reminder, estimated 5,000 reminders
- **AuditLogs Table**: ~2KB per event, 30-day retention, estimated 100,000 events

**Total Estimated Storage**: ~50MB for 1,000 users with moderate activity

### Kafka (Ephemeral Storage)
- **Task Events**: 7-day retention, ~1KB per event, estimated 10,000 events/day
- **Reminder Events**: 1-day retention, ~500 bytes per event, estimated 1,000 events/day
- **Audit Events**: 30-day retention, ~2KB per event, estimated 10,000 events/day

**Total Estimated Kafka Storage**: ~100MB for 30-day retention

### Dapr State Store (PostgreSQL)
- **Idempotency Keys**: 24-hour TTL, ~100 bytes per key, estimated 10,000 keys
- **Total Estimated Storage**: ~1MB

## Performance Considerations

### Event Publishing Latency
- **Target**: <50ms from API call to Kafka publish
- **Bottlenecks**: Dapr sidecar overhead, Kafka broker latency
- **Mitigation**: Use async publishing, batch events if needed

### Event Processing Latency
- **Target**: <500ms from Kafka publish to consumer processing
- **Bottlenecks**: Consumer processing time, idempotency checks
- **Mitigation**: Optimize database queries, use Dapr State Store caching

### SSE Delivery Latency
- **Target**: <2 seconds from event publish to frontend update
- **Bottlenecks**: SSE connection overhead, network latency
- **Mitigation**: Keep SSE connections alive, use HTTP/2

---

## Security Considerations

### Event Data
- All events include `user_id` for access control
- Sensitive data (passwords, tokens) never included in events
- Event payloads validated against schema before publishing

### Access Control
- SSE connections authenticated via JWT token
- Consumers filter events by `user_id` to prevent data leakage
- Dapr components use Kubernetes secrets for credentials
